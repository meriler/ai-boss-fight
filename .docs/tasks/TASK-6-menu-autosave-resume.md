## Технические заметки
- **Решение по месту хранения menu-полей (принято здесь).** Кладём внутрь существующего `g` как вложенный `g.menu = {pending, taps, baseline, best, cycleSets, lastCheckAt}`. Почему: `loadSave` (:827) проверяет только наличие `s.g` и типы `ex/counts` — новый вложенный ключ не ломает валидацию; `applySave` (:854) уже делает `Object.assign(GUIDE, {...s.g...})` — рядом дописываем восстановление `MENU`. Плоские sibling-поля (`s.menuPending` и т.п.) тоже прошли бы валидацию, но `g` — уже согласованный контейнер guide-состояния, туда логичнее. Обратная совместимость: `s.g.menu === undefined` → `MENU` не мутируется.
- **Решение по `ms` для menu-сейва (принято здесь).** menu-добор идёт ПОСЛЕ финала, поэтому веха остаётся `'final'` (ранг 5, максимум в `SAVE_RANK`) — новый ранг не вводим, откат вехи внутри цикла (:805) menu-сейв не понижает. Отличие «обычный финал» vs «финал с недоигранным добором» несёт флаг `g.menu.pending`, по нему и ветвится `resumeFlow`. Если TASK-3 предпочтёт отдельный `menuTask`-цикл — синхронизировать: главное, чтобы `pending` однозначно говорил resume «восстанови меню, не финал».
- Дебаунс `addExample._t` (:890) НЕ убирать — он остаётся для post-final съёмки в лаборатории; для menu-набора добавляется ОТДЕЛЬНЫЙ синхронный вызов по событию «набор 3/3 завершён» (TASK-3), чтобы не зависеть от 1,2 с.
- `resumeFlow` уже защищён от битого снапшота (try/catch на `applySave` :1959) — восстановление `MENU` держать внутри той же транзакционной логики: битый `g.menu` не должен ронять resume в «Не смог прочитать сохранёнку».
- Приватность/размер: menu-поля — только числа и ключи квадрантов (`taps` — массив вида `t2a/t2b/t1a/t1b`), кадры/эмбеддинги туда не писать.
